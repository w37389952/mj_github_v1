# 데이터 소스 검증 결과 (2026-08-07 실제 호출)

브리프 §4의 "미확인 사항"을 실제 API 호출로 검증한 기록.

## 결론: 인증키 발급은 장벽이 아니다

| 경로 | 인증키 | 심사 | 비고 |
|---|---|---|---|
| 서울 열린데이터광장 샘플키 (`sample`) | 불필요 | 없음 | **요청당 5건 제한** — 개발/검증용 |
| 서울 열린데이터광장 일반키 | 회원가입 후 즉시 발급 | 없음 | 개인 발급 가능 |
| data.go.kr 일반 인증키 | 활용신청 필요 | 자동승인 | 심의 없이 신청 즉시 승인 |

즉 "일반인은 못 받는다"는 걱정은 사실이 아니다. 다만 **`sample` 키만으로 실제 운영은 불가**하다
(요청당 5건 제한). 개발·필드 검증까지는 키 없이 전부 가능하다.

## 살아있는 서비스

브리프 §4의 코드 추정이 **맞았다.** LOCALDATA 시절 `07_24_05_P` / `07_24_04_P`가
서울 열린데이터광장에서는 다음 이름으로 그대로 서비스 중이다.

```
휴게음식점  LOCALDATA_072405   146,710건
일반음식점  LOCALDATA_072404   536,045건
```

호출 형식 (인증키 자리에 `sample`을 넣으면 키 없이 5건까지 확인 가능):

```
http://openapi.seoul.go.kr:8088/{KEY}/json/LOCALDATA_072405/{시작}/{끝}/
```

## ✅ 해소됨: 데이터는 아직 살아있다 (2026-08-07 전량 스캔)

발급받은 인증키로 `LOCALDATA_072405` 전량(146,710건)을 스캔한 결과:

- **최신 인허가일자 `2026-08-04`** — 스캔 시점 기준 3일 전. 정상 갱신 중이다.
- 최근 영업일마다 하루 16~37건의 휴게음식점이 새로 등록된다.
- 영업중(`TRDSTATEGBN=01`) 휴게음식점 37,095건.

즉 아래 "공식 종료" 우려는 **페이지만 내려간 것**이고 데이터 자체는 현행이다.
다만 SLA가 없는 상태인 것은 여전하므로, 수집이 갑자기 실패하면 data.go.kr 표준데이터로
갈아탈 준비는 해둘 것.

- 휴게음식점에 `제과점영업`이라는 값은 **없다.** 실제 값은 `과자점`이다.
- 일반음식점은 `카페`가 아니라 **`까페`**(쌍기역)로 표기된다.

`UPTAE`로 범위를 좁힐 때는 이 정확한 표기를 써야 한다. 오타 하나면 조용히 0건이 된다.

## ⚠️ 남아있는 위험: 이 API는 "공식적으로는" 이미 종료됐다

서울 열린데이터광장의 **인허가 관련 데이터셋 페이지는 전부 종료 상태**다. 확인한 것:

| 데이터셋 | 페이지 상태 |
|---|---|
| OA-16095 서울시 휴게음식점 인허가 정보 (통합) | 종료 |
| OA-18693 구로구 휴게음식점 인허가 정보 (구별) | 종료 |
| OA-13663 서울시 식품위생업소 현황 | 종료 |

브리프 §3-1에 적힌 "LOCALDATA 2026-04-16 폐쇄, data.go.kr으로 통합"과 일치한다.
그런데 **`LOCALDATA_072404/072405` OpenAPI 엔드포인트는 여전히 정상 응답한다.**
페이지만 내리고 엔드포인트는 아직 살려둔 상태로 보인다.

여기서 나오는 위험 두 가지:

1. **예고 없이 끊길 수 있다.** 공식 종료된 서비스이므로 SLA가 없다.
2. **데이터가 갱신을 멈췄을 가능성.** 응답에 남아있는 `UPDATEDT`가 `2026-05-01`,
   `2026-01-14`였는데, 5건만 볼 수 있어서 최신 데이터가 들어오는지 확인하지 못했다.
   **만약 4월 이후로 멈춰 있다면 "매일 신규 카페" 자체가 성립하지 않는다.**
   이것이 지금 파이프라인 전체에서 가장 먼저 확인해야 할 항목이다.

키를 받은 뒤 `AUDIT=1`로 전량을 받아 `APVPERMYMD`의 최댓값을 확인할 것.
최근 며칠 내 날짜가 있으면 정상, 4월 언저리에서 멈춰 있으면 아래 대안으로 갈아타야 한다.

### 대안: data.go.kr 표준데이터

[전국일반음식점표준데이터](https://www.data.go.kr/data/15096283/standard.do) 기준으로 확인한 조건:

- 활용신청 **자동승인**, 무료, 이용허락범위 제한 없음
- **매일 갱신** (2일 전 기준으로 현행화)
- 213만 행, **기관 자체 CSV 다운로드 URL 제공** → 오픈API 호출량 문제에서 자유롭다

휴게음식점 표준데이터도 같은 계열로 존재한다. 서울 API가 멈춰 있다면 이쪽이 정답이다.

## 함정: 검색 결과가 거짓말을 한다

`서울시 식품위생업소 현황`(OA-13663)은 검색 목록에 **수정일자 2026-08-07**로 떠 있지만,
상세 페이지로 들어가면 "해당 데이터는 종료된 서비스입니다"가 뜬다. FILE 탭의 대량 다운로드도
동작하지 않는다(빈 HTML 응답). 검색 인덱스가 갱신되지 않은 것이므로,
**목록의 수정일자를 신뢰하지 말고 반드시 실제 호출로 확인할 것.**

반면 `LOCALDATA_072404/072405` OpenAPI는 정상 동작한다. 웹페이지가 죽은 것과
API가 죽은 것은 별개다.

## 확인된 실제 응답 필드

추정이 아니라 실제 응답에서 그대로 옮긴 것:

| 필드 | 의미 | 예시 |
|---|---|---|
| `MGTNO` | 관리번호 (고유키, 중복제거용) | `3170000-104-2001-06863` |
| `BPLCNM` | 사업장명(상호) | `카페네스카페시흥까르푸점` |
| `APVPERMYMD` | 인허가일자 | `2001-09-12` + 우측 공백 패딩 |
| `TRDSTATEGBN` / `TRDSTATENM` | 영업상태 | `01`=영업/정상, `03`=폐업 |
| `DCBYMD` | 폐업일자 | |
| `RDNWHLADDR` | 도로명주소 | 없는 건이 많음 |
| `SITEWHLADDR` | 지번주소 | 도로명 없을 때 대체 |
| `UPTAENM` | 업태구분명 | `커피숍`, `한식` |
| `SITETEL` / `SITEAREA` | 전화번호 / 면적 | |
| `X`, `Y` | 좌표 | `191152.43`, `438865.16` |
| `LASTMODTS` / `UPDATEDT` | 최종수정 / 갱신 시각 | |

주의할 점 두 가지:

- **문자열 값에 우측 공백 패딩이 붙는다** (`"2001-09-12              "`). 반드시 `strip()`.
- **`X`/`Y`는 위경도가 아니다.** 브리프 §7 경고대로 TM 좌표(EPSG:5174)다.
  지도 표시가 필요하면 WGS84 변환이 필요하다. 현재 대시보드는 변환을 피하려고
  상호명+주소로 네이버 지도 검색 링크를 거는 방식을 쓴다.

## 원본 갱신 시각 — 매일 22:17~22:48 (KST)

수집 시각을 원본 갱신 직후로 맞추기 위해 조사했다. 응답의 `UPDATEDT`(갱신 시각)를
`LOCALDATA_072405` 전량 146,744건에서 뽑아 분포를 봤다.

**지난 30일간 갱신된 1,746건이 100% 22시대에 몰려 있다.** 다른 시간대는 하나도 없다.

분 단위로 보면 두 덩어리로 나뉜다:

| 시각 | 건수(8월 이후) |
|---|---|
| 22:17~22:21 | 233 |
| 22:48 | 58 |

날짜별로 첫 건과 마지막 건을 보면 시작·종료가 거의 초 단위로 일정하다:

```
2026-08-01: 22:17:56 ~ 22:48:01
2026-08-04: 22:18:00 ~ 22:48:01
2026-08-05: 22:17:58 ~ 22:48:01
2026-08-06: 22:18:00 ~ 22:48:00
```

즉 **매일 밤 22:17에 시작해 22:48에 끝나는 배치**다. 따라서 수집은 그 뒤인
**23:30 KST(= 14:30 UTC)** 에 돌린다. 배치 종료 42분 뒤라 여유가 있고,
GitHub Actions는 정각에 작업이 몰려 밀리므로 30분에 맞췄다.

주의: 이것은 *데이터가 시스템에 반영되는* 시각이다. 인허가 신고일(`APVPERMYMD`)과는
여전히 2~3일 시차가 있다. 밤 10시 배치에 들어오는 건 대체로 2~3일 전에 신고된 건이다.

## 기존에 쓰던 사이트들과의 관계

- **덤덤(dumbndumber.co.kr)** — 하단에 "음식점 정보출처 : 행정안전부 한국지역정보개발원"이라고
  표기되어 있다. 이는 **지방행정 인허가데이터(구 LOCALDATA)**, 즉 지금 우리가 쓰는 것과
  **동일한 원본**이다. 이 사이트는 그 데이터를 받아서 보여주는 중간 단계일 뿐이다.
  화면에는 상호명·업종·주소만 나오고 **인허가일자가 없어서** "이번 주 신규"를 가릴 수 없다.
  (URL에 `jongnogu`를 넣어도 전남·광주 목록이 나오는 등 지역 필터도 정상 동작하지 않는다.)
- **머니핀(moneypin.biz/bizno)** — 사업자등록번호 조회 기반 유료 서비스.
  브리프 §2에서 이미 배제한 접근이다.

정리하면 **우리는 덤덤보다 한 단계 위(원본)에서 직접 받고 있다.** 남이 올려주길 기다릴 필요가
없고, 인허가일자가 있어서 신규 여부를 정확히 가릴 수 있으며, 구독료도 들지 않는다.

## 호출량

- 요청당 **최대 1,000건**. 일일 호출 건수 제한은 일반 인증키에 명시되어 있지 않다
  (1,000건/일 제한은 실시간 지하철 인증키 전용이다).
- **날짜 범위 필터는 없다.** 요청 경로 뒤에 날짜를 붙여도 무시된다.
  따라서 매 실행마다 전량 스캔이 필요하다: 휴게음식점 147회 + 일반음식점 537회 = **약 684회**.
  실측으로 문제없이 완주했다.
- 호출량이 부담되면 data.go.kr 표준데이터의 CSV 직접 다운로드로 바꾸는 편이 낫다
  (1회 다운로드로 끝난다).
